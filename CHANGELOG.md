# Changelog

All notable changes to this project are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Dashboard: a failure's *First seen* date shows beside its triage state on the flow page and in the history (#84).
- Dashboard: every live page (overview, pipeline, flow, runner and device) has one polite status region that reads run events out in batches, at most once every five seconds: a run starting or ending, a flow failing or being interrupted, a pipeline's verdict changing. Log lines and counts are never read out (#149).
- Agent: each emulator's `qemu-system-*` process is matched to its serial by its console port, and its CPU and resident memory are sent with the device's samples (`emu_cpu_pct`, `emu_rss_bytes`, #39).
- Agent: device samples carry the AVD name and the API level, and the resumed activity of a device on which a flow failed (#39). The server stores them in `device_samples` (migration 0019).
- Dashboard: an *Active emulators* tile on the overview counts emulators seen in the last two minutes that adb reports online (#123).
- Agent: while the host is under pressure (PSI CPU `some avg10` at least 40, PSI memory at least 20, or host CPU at least 95 %, CPU alone on macOS), host and process metrics are sampled every 15 s instead of 5 s and the devices' guest CPU and memory reads are skipped. The agent leaves that state after three calm samples (#39).
- Dashboard: a flow whose app crashed shows "App crashed: <exception> in <package>" above Maestro's failure, with a link to the device logcat excerpt (or a note that none was uploaded); the flow's result and failure message stay Maestro's (#152).
- Server: API keys expire after `api.api_key_ttl_days` (90 by default) unless `fleet api-key create --expires-in-days` says otherwise. `api.api_key_ttl_days` must be above 0.
- Dashboard: a flow whose device was lost during it is labelled "Failed · infrastructure (device lost)" above Maestro's failure, on the flow page and in history, with the evidence that made the call (the failure's `DeviceServerDiedException` and the agent's `commands_not_final` warning) and the provenance of the failure. The label needs both halves of that evidence; the flow stays failed. The REST flow and history entries carry `infrastructure` with `evidence`, `warning`, `source` and `finality`. `fleet-agent inspect` applies the same rule (#145).
- Server: `GET /api/v1/flows/{id}/page` redirects a signed-in reader to the flow's screen D (`/flows/{id}?project=<slug>`), for a flow known only by its ID. A reader without a role on the flow's project gets the answer for a missing flow (#71).
- Agent: the job summary links each flow that did not pass to its screen D, when `FLEET_SERVER` is set (#71).
- Examples: the composite action's `install` input (default `true`) runs the `fleet-agent` already on `PATH` with `false`, and its `summary-file` output names the job summary file (#71).
- CI: the `action-smoke` job runs the composite action on the repository's own agent over a fake Maestro that replays the `suite` fixture, with a quoted argument, and checks the job summary and Maestro's exit status (#71).
- CI: the claim lattice's property tests run at `PROPTEST_CASES=20000` on every push and pull request (#46).
- Failure triage: a maintainer marks a failure fingerprint Known (with the issue that tracks it) or Resolved, or clears it. The state shows on history rows, on the failure groups of a flow's stats and on the flow page's failure band. Every fingerprint records when it was first seen, and every change is audited (`PUT` and `DELETE /api/v1/projects/{project}/failures/{fingerprint}/triage`; migration 0020, #84).

- Agent: an offline run (no `FLEET_SERVER`, such as a fork pull request) writes `fleet-bundle.tar.zst` to its run directory: its journal and the artifacts it would have uploaded, each redacted as a live upload is. The run's output and exit status are unchanged (#83).
- Agent: `fleet-agent publish <bundle or Maestro output directory>` sends a finished run to the server as a new, imported run. Live console output is recorded as debug-log evidence, not as live (#83).
- Agent: a Maestro HTML report is uploaded as an `html_report` artifact when the run wrote it: the file `--output` names for `--format html` or `html-detailed`, or Maestro's default `report.html` in the working directory without `--output` (redacted like a log; not uploaded above 16 MiB; a report left by an earlier run is ignored with a `report_stale` warning). An upload that fails never changes the run's result (#43).
- Dashboard and REST: a published run is labelled *Published* wherever runs and flows are shown, and the REST API carries `origin` (`live` or `published`) on agent runs, flows and history entries. The server stores it in `agent_runs.origin` (migration 0021).
- Agent: a published Maestro output directory without `meta.json` keeps the times its files record (the `maestro.log` records and the flows' `commands.json`), not the 1970 replay epoch.
- Server: a published run is filed under the day it started (`run_day`), not the day it was published. A run older than the journal retention is refused with the reason.
- Agent and server: artifacts can be uploaded straight to S3 with a presigned `PUT` (issue #43, PLAN §7.6, ADR-0007). The agent asks with `direct: true`; the server answers `presigned` with a staging URL signed for the file's SHA-256, and reads the staged bytes once, at `complete`, and verifies them as before. A store that cannot presign, or a direct upload that fails, is relayed as before. New server setting `storage.s3.public_endpoint` (the host agents reach). Protocol: additive `UploadRequest::direct` and `UploadGrant::Presigned`; schemas regenerated. Repeated completions return the recorded outcome and never re-read staged bytes.
- Server: the usercontent origin answers HTTP `Range` requests for artifacts: a single byte range is `206 Partial Content` with `Content-Range`, an unsatisfiable one is `416`, and every answer carries `Accept-Ranges: bytes` (#43).

- Agent: a final `commands.json` whose flow the log never started is warned on its agent run (`commands_flow_unnamed`) instead of being ignored. The server keeps the warning on the run (`file_warnings`, migration 0025), and the job's entry on the pipeline page says so; no flow is created for it (#148).
- Docs: the operator guide's Upgrades section covers backups before an upgrade, forward-only migrations and their checksums, agent and server protocol versions, rollback by restore, and how to rehearse an upgrade.
- Tooling: `cargo xtask upgrade-rehearsal` exports each release tag's migrations from git, seeds rows under each release's schema, migrates to the current tree and checks that the rows and the current read paths survive (`crates/fleet-store/tests/upgrade.rs`). CI runs it on every push and pull request.

### Changed

- Dashboard: the *Active emulators* tile sits beside the runners on the overview, not in the readout strip (#123).
- Dashboard: a pipeline whose flow failed reads *Failed* while its jobs are still running; the verdict follows its flows (#149).
- Dashboard: the status words follow one vocabulary. *Completed* replaces *Finished*, *Closed* and a job's closed lifecycle without an outcome; *Interrupted* replaces *Cancelled*; *Running* covers starting, finalizing and reporting; *Not started* replaces *No jobs yet* (#149).
- Dashboard: a settled result carries no provenance badge of its own. Rows mark only *Provisional*, *Inferred*, *Missing* and *Stale* values; each page or section states *Verified* or *Observed* once (#149).
- Dashboard: on a phone the top bar shows the brand mark and the live indicator. The pages, the project and the account are behind the ⋯ button (#149).
- Dashboard: the sign-in prompt and error notices are hairline-ruled rather than bordered boxes, and so is the log viewer (#149).

### Fixed

- Agent: a live run follows Maestro's files for two more layouts, which the captured fixtures now cover: a workspace config's `testOutputDir` (read from `--config`, or from a `config.yaml` in a directory the command names, and overridden by `--test-output-dir`), and `--flatten-debug-output` with `--test-output-dir` or with `--debug-output` and `--test-output-dir`. `--flatten-debug-output` alone writes into Maestro's `user.home`, which the agent now reads as the JVM does (`-Duser.home` in `JAVA_OPTS` or `MAESTRO_OPTS`, else the account's home), not from `$HOME` (#148).
- Agent: a command that already has `--flatten-debug-output` is never given a second one. Maestro rejects a repeated flag with exit 2 (captured: `paths-flatten-repeated`), so the run failed before it started.
- Agent: two Maestro runs in one tree no longer trade their steps. A run's directory is the one its own process holds its session log open in, not the oldest one created since it started. With no process to ask, a single candidate is taken and several are not (#148).
- Agent: the watcher reads a shared flattened directory (the home directory without `--debug-output`) only for folders created since the run started, and on a backoff of at most once a second while nothing new appears, so it no longer reads every entry of the home directory on each 50 ms poll (#148).
- Dashboard: a step the log opened and never ended, which the flow's final `commands.json` does not list either, is Missing rather than Provisional. Every other step is settled from the file as before (#148).
- Dashboard: a step row still read from the live log is marked Stale once its run goes quiet, the same rule as the flow's own badge, and its open steps are marked Inferred and read Unknown when the server abandons the run (#148).
- Agent: a live run settles its steps from `commands.json` wherever the command's own flags put Maestro's files: `--debug-output`, `--test-output-dir`, `--flatten-debug-output` in any combination, or none of them with `--fleet-rewrite=off`. The watcher used to follow only the agent's flattened directory, so those runs left their steps Provisional until a replay (#148).
- Dashboard: a flow's step rows stay Provisional after the flow is Verified. Once the flow ends, its final `commands.json` settles the steps the log reported: each command is paired with the step at the same depth and of the same command kind, and a paired row takes the file's result and timing and is Verified. Unpaired steps stay Provisional, and the Steps section says when steps could not be matched or when the log and the file disagree on a status (the file's status is shown). A settled step row carries no badge of its own, since its section states Verified once; a row shows its own badge only when it is Provisional, Inferred, Missing or Stale (#149). A cut-short, empty, aborted or unrecognised `commands.json` settles nothing. `step.ended` carries the file's start and duration as an optional `timing` (protocol additive change; schema regenerated). Migration 0023 keeps the alignment warnings on the flow (#148).
- Examples: the composite action splits its `command` input as a shell does for quotes and backslashes (`maestro test "my flows/"` passes one argument). It used to split on every whitespace, so a quoted argument broke (#71).
- Server: `fleet api-key create --project <slug>` on a configured project keeps the project's name; it used to rename the project to its slug until the next `serve` start.
- Agent: `fleet-agent publish` with no credential (no `FLEET_TOKEN`, no CI OIDC variables) fails before it reads or sends anything, and names the variables to set; it used to report the run as refused by the server.
- Agent: `fleet-agent publish` of a run the server refuses (older than the journal retention) exits at once with the reason. It used to wait out the upload budget (`FLEET_UPLOAD_TIMEOUT`, 120 s by default) first.
- Server: pull request runs (trust `pr`) and untrusted runs are kept out of flow stats, the duration summary and chart, failure groups and flakiness verdicts. They stay in the history and on their own run pages.
- Agent: a run with no credential (no `FLEET_TOKEN`, or an empty one, and no OIDC request) runs offline. It no longer attempts an unauthenticated connection, which sent the run's CI facts to the server.
- Server: the OIDC key-set client no longer follows redirects, so a redirected discovery document is refused.
- Server: token-shaped text in step, flow, report and app-crash events is redacted on ingest, before it is journaled or stored.
- Server: the dashboard CSP forbids `<object>` and `<base>`, and open browser sockets close when their sign-in ends (`api.session_recheck_ms`, 30 s by default). Signed artifact links last at most 300 s. CI OIDC tokens without a `jti` are refused.
- Blob: an SVG with an XML prolog is refused as a JUnit report.
- Maestro: escape strings (OSC, DCS and others) are removed with their payload, so an OSC 8 link or OSC 52 clipboard write never reaches a log line.
- Xtask lint: raw HTML injection (`inner_html`) is refused in Rust sources.
- Dashboard: no page scrolls sideways at 1440 px or 390 px. Long flow names, run ids and URLs wrap, wide tables scroll inside their own box, and the phone's navigation shrinks instead of pushing the account off the screen (#149).

Temperature is no longer charted, since no agent reports it (for a device too); the API still returns it as unavailable.

- Dashboard: history and compare follow the redesign: a filter band with underlined fields, one "Verified" for a table whose rows are all final, a stats panel that shows only the figures that say something, an answer first on compare ("Failures only in B") with a Swap button, and sections that state their provenance once.
- Dashboard: the flow page is redesigned around the failure: steps are numbered as in the flow file (Maestro's setup commands fold into one unnumbered "Setup" row), a failure band names the failed step, its command and message (with a copy button), a history strip shows the flow's last executions, the verdict says why it is verified or provisional, and steps, evidence and logs sit in three panes.

## [0.1.0-alpha.2] - 2026-11-07

### Added

- Agent: a failed flow's device logcat is uploaded as an excerpt: the lines of the failing step's window (10 s before it to 2 s after it), redacted line by line, at most 512 KiB, keeping the newest lines and saying when older ones were cut. The window is placed on UTC by the log's own last line, so a log whose clock cannot be told from the failure's is not sent (#75).
- Agent: an app that crashes during a flow is journaled as `app.crashed` (package and exception, from Maestro's `crash-report.txt`) on that flow. The flow's verdict stays Maestro's own (#75).
- Server: the `device_logcat` artifact class, a text file with its own size limit (`artifacts.max_bytes.device_logcat`, 512 KiB) (#75).
- Dashboard: screen D offers a failed flow's device logcat excerpt as a download, labelled "Device logcat excerpt" (#75).
- Agent: at run end, `GITHUB_STEP_SUMMARY` gets a short Markdown summary: outcome counts, the flows that did not pass with their provenance and reason, and a dashboard link when `FLEET_SERVER` is set. A summary that cannot be written costs one notice; Maestro's output and exit status never change (#71).
- Agent: the devices Maestro drives are sampled every 30 s with one read-only adb probe each: adb's state, whether `sys.boot_completed` is set, and the guest's CPU and available memory (`guest`, unknown when adb does not answer). The server stores them in `device_samples` and screen C serves them (#39).
- Examples: a composite GitHub Action, `examples/github-actions/fleet-agent`, installs a pinned, checksum-verified agent release and runs a Maestro command under it (#71).
- Dashboard: a flow's stats panel says how many of its failed runs a lost device excluded from flakiness (`excluded` on the flow's verdict; "2 runs excluded (device lost)"), and says nothing when there are none (#72).
- Agent: a failing step's UI hierarchy (`screen-hierarchy/step-NNN-….json`) is uploaded as a `failure_hierarchy` artifact with its on-screen text values replaced by `[REDACTED]` (the tree and its attributes are kept); screen D lists it under its step, and the failing step's comes first (#74).
- Agent: step events carry `depth`, `parent` and `attempt` where Maestro's log shows them (a step inside `runFlow`, `retry` or `repeat`, and the retry attempt that ran it). The flow page nests steps under their block and shows the attempt of a retried step, from `GET /api/v1/projects/{project}/flows/{execution}`, whose `steps` are now a tree with `children` (#38).
- Server: per-IP limits on the pre-auth routes (agent token exchange, browser sign-in and callback) and per-credential limits on agent connections, answered with `429 Too Many Requests` and `Retry-After`; an agent socket's events are paced, never dropped. Client IPs come from `trusted_proxies` (#35).
- Server: viewer REST reads and live socket upgrades are limited per viewer credential (a viewer token or a browser session), answered with `429 Too Many Requests` and `Retry-After`; the dashboard waits that long and keeps its last data instead of erroring (#35).

### Changed

- Dashboard: the pipeline's plan table reads a small plan endpoint (`GET /api/v1/projects/{project}/attempts/{attempt}/plans`) and refetches it only when a planned shard's runs change or the attempt ends, instead of the whole attempt snapshot on every live update; its own fetch error shows in the table (#115).
- Server: the image takes wasm-opt, tailwindcss and wasm-bindgen from a cached build layer, pinned by checksum, so a source change no longer downloads them again and a stalled download resumes (deploy/docker).

### Fixed

- Agent: reconnects to a refusing server back off again. The jitter read the clock's low nanoseconds, which are always zero on macOS, so every delay was zero and the agent retried about every 1.5 ms (3,108 attempts in 5 s); jitter now comes from OS randomness, and the server's goaway reconnect jitter, which had the same bug, too (#90).
- Agent: a failed write to `journal.jsonl` (disk full, I/O error) stops the journal like the cap does: one `journal.truncated` line names the error, the run's warning names the first missing seq, and `fleet-agent inspect` reports it. Before, the error was dropped silently (#112).
- Dashboard: a flow's evidence keeps its state when its signed links renew (about every four minutes): the screenshot zoom and selection, and the log search, stay put instead of resetting, and the evidence card no longer rebuilds on every live update of the flow. A tooltip hides on Escape from anywhere while it is shown, not only from inside its trigger (#41).
- Server: a run whose socket another instance holds shows `online` or `stale` from its persisted contact, as on the instance holding it, instead of always `stale` (#114).
- Server: a worker's Maestro and agent figures are one series per agent run, raw and in the minute and hour aggregates, so runs that share a runner no longer merge or interleave; the runner's latest reading carries only the machine's figures. The dashboard's worker page draws one line per run (#42).
- Agent: after Maestro exits, the agent keeps draining its output while the CI log is still taking it, and gives up on an output pump after 2 s with no reads and nothing held for the log, or 10 s after the exit at most, so a backed-up log no longer loses its tail and a grandchild that keeps writing cannot hold the exit (#124).
- Server: the OpenAPI document describes a flow's nested step tree without recursing, so `GET /api/v1/openapi.json` no longer overflows the stack; `StepView.children` is an array of `StepView` references.

## [0.1.0-alpha.1] - 2026-11-06

### Added

- Planner: the manifest records what an equal-count split of the same flows would have produced by the same estimates (`equalCountEstimatedSeconds`), so a plan can state its saving over that split (#81).
- Dashboard: a pipeline with a Fleet plan shows each shard's planned and actual time (first flow start to last flow end) and the slowest shard's saving over an equal-count split (#81).
- Server: with several instances on one database, a change committed through one instance reaches browsers on the others as a live delta (Postgres `NOTIFY`/`LISTEN`), not only after a resync (#34).
- Agent: host samples carry the load average, CPU cores, swap and Linux pressure stall information (CPU, memory, I/O); screen C charts them and the worker page shows the core count, with "Not reported" for what an agent doesn't send (#42).
- Fleet Planner (ADR-0013): `fleet-planner plan` splits a Maestro suite into CI shards. It finds flows the way Maestro does (`config.yaml` globs, tags, `executionOrder`), balances shards Longest Processing Time first from Fleet history (or an even split without it), writes an immutable manifest and a GitHub Actions matrix, and publishes the plan. `fleet-agent run --plan` runs one shard with the plan's workspace config, and refuses an empty shard or a command that would select flows itself.
- The agent falls back to HTTPS batch transport after repeated blocked WebSocket upgrades, with server-authoritative resume and telemetry acknowledgments.
- Generated protocol JSON Schemas, golden wire frames and a CI freshness check.
- A pinned Maestro nightly emulator workflow and a captured absolute-path regression fixture.
- Agent: `cargo xtask bench-overhead` measures the agent's overhead (I10) by running the fake-Maestro suite with and without it, reporting the duration delta, the agent's CPU time and its peak memory.
- Agent: the Maestro version comes from the session log's own version line, and is recorded once per run as `maestro.detected` (no extra `maestro --version` process). The server keeps it on the run and in the run's condition fingerprint; a version outside Fleet's profile is warned about on stderr and recorded with `profile_supported: false` (#73).
- M5 exit: screen D shows a failed flow's evidence from the usercontent origin: the failure screenshot in the screenshot viewer (tied to the step named in its file name), the Maestro log in the log viewer opened at the failing step of that flow (the step tree moves it; "Jump to the failing step" returns), command timings from `commands.json`, a link to the Maestro HTML report that opens sandboxed on the usercontent origin, downloads, refused uploads with their reasons, and honest empty states (nothing uploaded, no usercontent origin). The dashboard's CSP allows exactly the configured usercontent origin in `img-src` and `connect-src`. `fleet-e2e` proves acceptance criteria 7, 8 and 9 and invariant I7 in a real browser with the real agent. The step tree now sets `aria-level`, `aria-posinset` and `aria-setsize` (they were being written as `attr:aria-level`). User guide: "Investigating a failure".
- M5: retention (issue #45). The leader runs telemetry rollups (one-minute and one-hour, idempotent, late-data aware; unavailable readings stay unavailable), drops expired partitions of raw samples, the journal and steps (raw samples only once rolled up), deletes expired rollups and audit events, expires artifacts by retention class (failure evidence is promoted when its flow finalizes as failed; legal hold keeps an artifact), and deletes blob objects only when no artifact refers to them and after a grace period; leftover temp files of crashed local uploads are swept (`BlobStore::sweep_stale_uploads`). Migration 0009; `[retention]` server settings; operator guide section. The metrics endpoints serve ranges over 24 hours from the rollups.
- M5: screens E and F of the dashboard (History and Compare): `GET /api/v1/projects/{project}/history` (filters by flow, branch, outcome and time, bounded to 90 days, cursor pages, failure and condition fingerprints, flaky v1 verdicts naming the runs behind them), `…/flows/{name}/stats` (settled counts, p50/p90 duration of passes, the latest durations, failures grouped by fingerprint) and `…/compare?a=&b=` (flow-by-flow outcomes with explanations drawn from the sides' evidence only); the `/history` and `/compare` pages with URL-synced filters and attempt pickers; `fleet-loadgen` can set the commit, ref, architecture and failure pattern of a run.
- M4 exit: the browser acceptance suite (`fleet-e2e`, `m4_exit.rs`) proves, in a real browser against the real server, that a developer can follow a full run without CI logs and that acceptance criteria 2, 4, 5, 6 and 14 pass (plus 12 for sign-in): the real `fleet-agent` wrapping the fake Maestro replays a captured failing run, which is followed from the overview to the failed flow page without a refresh; progress counts toward a Fleet plan's total and is marked uncertain without one; ten simultaneous runs stay correct, and the page stays responsive; signing in works end to end against a wiremock identity provider (PKCE, `HttpOnly` cookie, group refusal, sign-out). The user guide gains "Watching a run" (screens A–D, the provenance legend, uncertain progress, stale and disconnected).
- M4: the dashboard: `fleet-ui` component kit, charts and swimlane timeline, log, screenshot and step views; screens A–D (overview, pipeline detail, runner and device detail, flow investigation) with live updates, resync after a server restart and stale and disconnected states; browser sign-in (OIDC code + PKCE, Postgres sessions, CSRF) and the `authorize` policy; REST reads for the four screens.
- M5: failure fingerprints (flow identity + failing step + message with numbers, UUIDs, timestamps, durations, paths, serials and addresses removed, versioned `v1:`), condition fingerprints (device, Maestro `major.minor`, OS/arch, host class, CI provider; missing facts read `unknown`) and flaky v1 (confirmed: pass and fail on one commit and condition; suspected: flip rate ≥ 0.2 over the last 20 default-branch runs; inferred outcomes never count as passes) in `fleet-core`; migration 0007 and the ingest transaction store both fingerprints when a flow's outcome is final (ADR-0009).
- M5: `fleet-blob`: the `BlobStore` contract (content-addressed per project; streaming `put` that verifies size and SHA-256, ranged `get`, `head`, idempotent `delete`, `list` for GC) with a local filesystem backend (atomic writes) and an S3-compatible one (`object_store`, path-style, custom endpoint; Garage is the reference), one contract suite run against both; `fleet-blob::verify`: size, SHA-256, magic bytes per artifact class and archive safety for zip and `tar.zst` (entry count, expansion limits, unsafe paths, links, devices, nested archives); `[storage]` server settings and the operator guide's storage section. No upload endpoints yet.
- M3: `fleet-loadgen` runs simulated agents against a real server (`--agents --devices --storm --duplicates`), replacing `mock-server`; `fleet-e2e` proves the M3 exit criteria (50 agents × 4 devices, reconnect storm, server restart mid-run, fixture replay matching `fleet-agent inspect`, jobs and same-serial emulators kept apart); the Docker image (`deploy/docker/Dockerfile`, cargo-chef + distroless) and the Compose reference deployment (Postgres 18, Garage, Caddy); operator guide and protocol reference.
- M3: `POST /api/v1/agent/token` exchanges a CI OIDC token (configured issuers only, RS256, JWKS cached and refetched on an unknown `kid`, `aud`/`exp`/`nbf`/`iat` checked, each `jti` once) for a short-lived agent token, matched by trust policies on immutable repository IDs (`fleet-core::trust`; `pull_request_target` and `dynamic` always refused), or exchanges an API key. Verified claims name the pipeline run and job. The agent does the exchange on GitHub Actions (#25), tunnels through `HTTP(S)_PROXY` with `NO_PROXY` and trusts `FLEET_CA_FILE` (#24). `fleet-e2e` runs the real agent against the real server.
- M3: the live hub and `/api/v1/live` (snapshot, then deltas in version order per attempt, `resync` for slow subscribers, `Origin` check), REST snapshots with a consistent `version` (`/api/v1/projects`, `…/attempts`, `…/attempts/{id}`), `/api/v1/openapi.json`, liveness (`online`/`stale`/`disconnected`/`completed`) and leader-only sweeps that detach silent runs and abandon expired ones (open flows become `unknown` from `server_inferred`, jobs `interrupted`), and Fleet plans (`POST /api/v1/plans`, immutable, planned totals before any job starts; #21). Reads need a viewer token until browser SSO (M4). The plan manifest type moved to `fleet-protocol::plan`.
- M3: the server ingests agents: `/api/v1/agent/ws` (`fleet.v1+json`: welcome with server-authoritative resume, ack after commit, `event_rejected`, `seq_gap`, fencing, pings, idle timeout, `goaway` + close 1012 on shutdown), the HTTPS batch fallback `POST /api/v1/agent/batch`, telemetry checkpoints with `telemetry_ack`, API-key auth, `/livez` and `/readyz`, and the `serve`, `migrate`, `check-config`, `healthcheck` and `api-key create` subcommands with figment configuration (TOML, `FLEET_*`, `*_FILE`).

### Changed

- Suspected flakiness requires five eligible runs. I6 now specifies supported redaction sources and encodings, withholds resolved command fields, and documents binary evidence access controls.
- Finalization uses a shorter flush budget when the server never answered the WebSocket upgrade during the run.
- Relicensed from PolyForm Internal Use 1.0.0 to the GNU AGPL v3 (`AGPL-3.0-only`); a commercial license is available on request (ADR-0012).
- Renamed the product to Fleet; the agent binary is `fleet-agent` (ADR-0011).
- Agent: `journal.jsonl` is capped at 256 MiB (`FLEET_JOURNAL_MAX_BYTES`, `--journal-max-bytes`). Past the cap it stops with one `journal.truncated` line, the run ends with one warning, and `fleet-agent inspect` reports the missing events; the server still gets every event (#37).

### Fixed

- Credential-bearing agent requests require TLS for remote hosts, and cleartext loopback traffic bypasses proxies. The sign-in callback preserves authenticated sessions.
- Ingest checks device and shard ownership, contains invalid NUL characters, rolls back rejected event effects, and rejects events after `run.ended` within the same batch.
- Agents reconnect silent sockets and replay spool records after disk-write failures. Live clients resnapshot missing changes, ignore superseded socket disconnects, and release idle ordering state.
- Flow history uses repository-relative report identities when the workspace is known. Running flows without a device display stale provenance, and history scans have a supporting index.
- Dashboard: the "Sign in" links were taken over by the client-side router and landed on "Page not found"; they now leave the single-page app (`rel="external"`) so the browser follows the redirect to the identity provider (found by the M4 exit tests).
- Agent: the outbox kept every unacked event in memory, so a long run with no server (offline mode) or an unreachable one grew without bound (I10). The spool file is now the source of truth, read back into a small send window; when the 64 MiB spool (or the window, with no spool) is exhausted the agent stops storing event bodies and sequences a `journal.gap` instead (I5), and the spool starts over once everything in it is acked. `fleet-agent flush` streams the spool instead of loading it.
- Server: a new agent run opening while another run's batch in the same job was mid-transaction could deadlock in Postgres (attempt and job rows locked in opposite orders); the batch was retried and nothing was lost, but the agent reconnected. `open_run` no longer locks the attempt row (found by the Compose smoke test).
- `fleet-loadgen`: `wss://` servers panicked for want of a rustls crypto provider; it now installs ring, as the agent does.
- Agent: a late-starting observer could read a flow's console result before the log line that starts it and split one flow into two; it now catches up on the log before applying console output (found by the M3 end-to-end tests).
- Server: a worker's "Last seen" and the overview's 24-hour worker filter only moved when an agent connected, so a long-running worker looked stale; the periodic liveness persist now also refreshes the worker's `last_seen_at`.
- Dashboard: history "Load more" could add a page fetched under the previous filter, or offer that filter's cursor until the new first page arrived; answers for an older filter are now dropped.
- Dashboard: a failed or interrupted flow's Failures badge now updates when its provenance settles (it was keyed without provenance, so the row kept the old badge until reload).
- Dashboard: Escape hides a tooltip without moving focus (WCAG 1.4.13); a `#L123` in the log's address scrolls to and highlights that line on load; a flow's screenshot and log links are retried after 5 s when a refresh fails for a transient reason, instead of staying expired until reload.
- Agent: nested steps (`runFlow`, `retry`, `repeat`) were paired with the wrong start, so parent steps stayed running and their ends appeared as unnamed steps; each end now closes its own step, and a step whose end arrives after the flow's console result is no longer dropped (#62).
- Agent: a transient write error to the CI log (a full non-blocking pipe, an interrupted flush) used to stop, or drop output from, Maestro's copy to the log. Output now reaches the log in full and in order: a slow log slows Maestro down (backpressure), and only a closed log stops the copy.
- Agent: failure screenshots and screen hierarchies are journalled against the step Maestro's `commands.json` says produced them (`artifacts[]`), instead of a step guessed from the file name; the file name is only the fallback for output without `artifacts[]`, and a file still waiting for its `commands.json` at run end keeps that fallback (#76).
- Dashboard: a failure screenshot links to the step Maestro's `artifacts[]` names, which the server now stores on the artifact (`step` in the artifact view, migration 0011); the file name is only the fallback for uploads without a stored step, and screenshots upload once their step is known (#76).
- Agent: at finalize, a server that was still answering `hello` when Maestro exited got the 3-second budget of an unreachable one, and uploads could hold back the journal's tail; the journal's tail is now sent first, and a server that answered the upgrade gets the full flush budget (#90).
- Server: flaky history no longer counts a failure whose message names a lost device (Maestro's `DeviceServerDiedException`) as flakiness, as ADR-0009 promises; such a run is excluded from the verdict (#72).
- Server: a flow's failure groups scanned every flow execution (the stats query filtered the project only on failure fingerprints), so they now use the history index; the leader's blob collection also deletes objects that no `blobs` row records once past the blob grace period (orphans a crash leaves behind), hourly.
- Release: the shipped third-party license notices leave out dev and build dependencies, so a test-only crate with an unaccepted license no longer fails the release build.
